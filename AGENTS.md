# AGENTS - Codex Workspace Rules

Актуально на: 2026-04-02

## 1. Priority and Scope

- Файл `AGENTS.md` является главным источником правил для Codex в этом workspace.
- При расхождении между markdown-документами всегда применяется `AGENTS.md`.
- `AGENT_HANDOFF.md` используется только как операционная сводка и не переопределяет policy.

## 2. Project Context

- Проект: web MVP техподдержки университета.
- Режим: web-only, Telegram вне ближайшего релизного scope.
- Маршрут запроса: `FAQ -> RAG -> Operator`.
- Стек: React/Vite (`frontend/`), FastAPI/SQLModel (`backend/`), PostgreSQL, Qdrant.

## 3. Session Bootstrap (0-10 min)

1. Открыть в порядке: `docs/README.md` -> `README.md` -> `AGENT_HANDOFF.md` -> `CURRENT_VERSION.md`.
2. Проверить состояние репозитория: `git status --short`.
3. Зафиксировать цель текущей сессии и критерии успеха в первом ответе пользователю.
4. Выполнить безопасную быструю диагностику окружения: `docker compose ps` (без изменения данных).
5. Выбрать первый безопасный шаг (read/check), только потом переходить к мутациям.
6. Все рабочие допущения фиксировать явно в ответе пользователю.
7. Если есть риск ошибки с высокой ценой (данные, прод-like конфиг, destructive-операции), сначала согласовать с пользователем.

## 4. Mandatory Work Rules

### 4.1 Docker Safety Rule

- Перед завершением работы или закрытием Docker Desktop выполнять: `docker compose down --remove-orphans`.
- `docker compose down -v --remove-orphans` использовать только при явной необходимости удалить volume.
- Локально запускать стек только с `compose.override.yml`; одиночный `compose.yml` не запускать.

### 4.2 Docker Incident Protocol

- Если Docker Desktop завис в `Starting`: закрыть Docker Desktop -> `wsl --shutdown` -> запустить Docker Desktop снова.
- После перезапуска проверить: `docker compose ps` и `docker info`.
- При повторе инцидента сохранять логи из `%LOCALAPPDATA%\Docker\log\host`.
- В handoff фиксировать время инцидента, симптомы и какие команды уже выполнялись.

### 4.3 Config and Secrets Discipline

- Не изменять `.env`, ключи и секреты без явного запроса пользователя.
- Не публиковать токены/секреты в логах, ответах, коммитах и скриншотах.

### 4.4 Commit Safety Rule

- Изменения в `.env` допускаются только локально; включать `.env` в commit запрещено без явного подтверждения пользователя.
- Для добавления файлов в commit использовать точечный `git add <path>`; избегать слепого `git add -A`/`git add .`.
- Перед каждым commit обязательно выполнить проверку: `git status --short` и `git diff --cached`.
- Если в staged-пуле обнаружены `.env`/секреты, остановить commit, снять файл(ы) со staging и согласовать дальнейшие действия с пользователем.

## 5. Execution Model

- По умолчанию работать в режиме `single-agent`.
- Декомпозиция на несколько агентов допустима только для независимых задач с явным разделением ответственности.
- Перед запуском параллельной работы убедиться, что области изменений не конфликтуют.
- Если требование неполное, выбрать разумное допущение, явно записать его и продолжить работу.

## 6. Tool Discipline

- Перед рискованной командой формулировать: цель, ожидаемый результат, условие отката.
- Рискованные команды: операции с Docker lifecycle, миграции, массовые файловые изменения, git-операции с историей.
- Запрещены скрытые destructive-действия.
- Запрещены destructive-команды без явного запроса пользователя (`git reset --hard`, массовые удаления, принудительные откаты).
- Перед рекурсивным удалением/перемещением проверять абсолютный путь и границы workspace.

## 7. Eval Loop

- Для backend-изменений: запуск релевантных backend-тестов + минимум один API/smoke сценарий.
- Для frontend-изменений: релевантные frontend/e2e проверки или сборка + минимум один UI smoke сценарий.
- Для docs/policy-изменений: проверка ссылок и consistency по ключевым правилам через `rg`.
- Для Docker/config-изменений: `docker compose config`, `docker compose ps`, проверка health критичных сервисов.
- Если проверка не выполнена, это обязательно указывается в отчете с причиной.

## 8. Engineering and Review Standards

- Делать минимально достаточные изменения без несвязанных рефакторингов.
- Сохранять совместимость API/контрактов, либо явно фиксировать breaking changes.
- В review сначала выделять Critical/High, затем Medium/Low.
- Если проблем не найдено, явно указывать residual risks и тестовые пробелы.

## 9. Explicit Prohibitions

- Не запускать локальный стек как одиночный `compose.yml` без `compose.override.yml`.
- Не выполнять destructive-команды без явного согласования.
- Не удалять и не откатывать чужие несвязанные изменения в рабочем дереве.
