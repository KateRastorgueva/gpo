# Лёгкий режим «Только поиск» на ноутбуке

Режим для проверки системы на обычном ноутбуке (16 ГБ RAM, без GPU). После
промаха FAQ система ищет ответ в загруженных документах и показывает
пользователю найденные фрагменты: название документа, оценку релевантности и
сам кусок текста. Языковая модель (Gemini, Ollama, AnythingLLM) не вызывается.

Как это устроено:

- поиск BM25 с русским стеммингом по чанкам в Postgres;
- контейнер Qdrant и модель embeddings не нужны (`VECTOR_SEARCH_ENABLED=false`);
- маршрутизация прежняя: FAQ → поиск → оператор. Посторонние вопросы, вопросы без
  найденного контекста и критичные темы (например, коллективный договор) уходят оператору;
- генерацию можно включить в любой момент, переключив движок в админке.

## Сколько это весит

| Что | Сколько |
|---|---|
| Контейнеры | 4: `db`, `prestart` (запускается один раз и завершается), `backend`, `frontend` |
| RAM backend | ~130 МБ в простое, ~200 МБ при поиске, до ~260 МБ во время загрузки 49 PDF |
| RAM Postgres | ~100–150 МБ |
| RAM frontend (nginx) | ~10 МБ |
| База с 49 документами | 17 МБ (3006 фрагментов, 3 млн символов) |
| Загрузка 49 PDF в базу | 41 с |
| Время ответа на вопрос | медиана 150–200 мс, максимум 650 мс (первый запрос после старта) |

Тяжелее всего первая сборка образов (`--build`): несколько минут и 1–2 ГБ RAM на
время сборки фронтенда. После сборки всё в сумме занимает меньше 0,5 ГБ RAM.

## Запуск

Docker Desktop должен быть запущен.

1. Обновите код (ветка этого PR или `master` после мержа).
2. В `.env` задайте:
   ```env
   RAG_PROVIDER=search_only
   VECTOR_SEARCH_ENABLED=false
   ```
   `RAG_PROVIDER` нужен только как значение по умолчанию: движок можно переключить и в админке.
3. Поднимите только нужные контейнеры. `db` и `prestart` стартуют сами как зависимости
   backend; Qdrant, AnythingLLM, adminer, traefik и mailcatcher не запускаются:
   ```bash
   docker compose up -d --build backend frontend
   ```
4. Откройте http://localhost:5173 и войдите администратором (`FIRST_SUPERUSER` из `.env`).
5. Перейдите в **Управление → Движки RAG**:
   - в «Пакетной загрузке» выберите **«Встроенная база (для «Только поиск»)»** и загрузите PDF.
     Берётся текстовый слой PDF, а также `.txt`, `.md`, `.html`. У сканов текстового слоя нет;
     для 8 сканов из «документы для ии» есть распознанные версии в папке проекта
     `new-docs-2026-10-21-ocr/`, загружайте их. Файл с тем же именем заменяется новой версией;
   - нажмите **«Только поиск, без генерации (лёгкий)»**.
6. Задайте вопрос в чате, например «Как оформить академический отпуск?».

Остановить: `docker compose stop`. Данные (база) сохраняются в томе `app-db-data`.

## Проверка автотестом

Тот же скрипт, что и для командного ПК, только с локальным адресом (фронтенд
проксирует `/api` в backend):

```bash
python scripts/host_autotest.py --base-url http://localhost:5173
```

Логин и пароль скрипт берёт из `.env`. Квоту облака он не тратит: в этом режиме
облако не вызывается.

## Только backend, без Docker для него

Если нужно проверить один backend (например, поиск после правки кода):

```bash
docker compose up -d db            # только база, ~100 МБ
cd backend
uv sync
POSTGRES_SERVER=localhost uv run alembic upgrade head
POSTGRES_SERVER=localhost uv run fastapi dev app/main.py
```

API будет на http://localhost:8000/docs. Загрузка документов и вопросы работают
через те же эндпоинты: `POST /api/v1/admin/rag/ingest/jobs` с `target: "local"` и
`POST /api/v1/support/ask`.

## Замеры (49 документов ТУСУР)

Прогон 2026-11-04 в облачной среде (не на ноутбуке): Postgres 16, один процесс
backend. 17 вопросов студентов, у каждого известен документ с ответом, плюс 3
посторонних вопроса и 1 критичный.

| Метрика | Результат |
|---|---|
| Нужный документ первым (hit@1) | 11 из 17 |
| Нужный документ в первой тройке (hit@3) | 13 из 17 |
| Ответов без оператора | 12 из 17, из них у 11 нужный документ в первой тройке |
| Посторонние вопросы → оператор | 3 из 3 |
| Критичный вопрос (коллективный договор) → оператор | да |
| `host_autotest.py` | вопросы 4 из 5; пятый ждёт документ `Izmeneniya_v_ustav`, которого не было в загруженном наборе |

Для сравнения, прошлые замеры на 17 вопросах: Gemini File Search 15/17 (8–40 с на ответ),
AnythingLLM с e5-small 14/17 (1–7 с). Наборы вопросов разные, поэтому сравнение примерное.

Где BM25 ошибается: синонимы и другая форма слова. «Сколько **стоит** обучение»
не находит приказ о **стоимости** обучения, «когда выплачивают стипендию» не
находит график выплаты. Такие вопросы уходят оператору, неверного ответа
пользователь не получает.

Порог: вопрос получает ответ, если лучший фрагмент содержит не меньше половины
значимых слов вопроса (взвешенных по редкости). Раньше порог был 0,25, и
посторонние вопросы («чемпионат мира по футболу», 0,46) получали «ответ».
Порог меняется в **Управление → Настройки → Маршрутизация → «Порог лучшего
фрагмента без векторов (BM25)»**.

## Если нужно больше

- **Генерация ответа по найденному:** движок «Встроенный поиск + генерация ответа (LLM)».
  Нужен ключ Google (облако, без нагрузки на ноутбук) или Ollama (тяжело: модель 8B — это 5+ ГБ RAM).
- **Векторный поиск:** `docker compose --profile qdrant up -d`, `VECTOR_SEARCH_ENABLED=true` (в
  `.env` или в «Настройках»), затем «Переиндексировать». Qdrant добавляет ~100 МБ RAM. Без
  настоящей модели embeddings выигрыша нет: в образе её нет, без ключа Google используется
  hashed-вектор, а по качеству это тот же лексический поиск. Локальная модель
  (`sentence-transformers`, extra `embeddings`) тянет PyTorch: ~1 ГБ RAM и ~2 ГБ образа; на
  этих документах не замерялась.
