# Лёгкая векторная добавка к поиску (BM25 + rubert-mini-frida)

Режим «Только поиск» (`search_only`) ищет по словам (BM25) и не находит синонимы:
«сколько стоит обучение» не попадает в «стоимость обучения». Добавка подмешивает поиск
по смыслу маленькой русской моделью [rubert-mini-frida](https://huggingface.co/sergeyzh/rubert-mini-frida)
(32 млн параметров, векторы по 312 чисел, ~125 МБ). Ни Qdrant, ни torch, ни GPU не нужны:
модель выполняется на numpy внутри backend, векторы чанков кэшируются в файл.

Добавка выключена по умолчанию. Включается в «Управление → Настройки → Движок ответов».

## Что скачается и сколько места займёт

| Что | Объём | Откуда |
|---|---|---|
| Файлы модели `_local/models/rubert-mini-frida` | 127 МБ | Hugging Face, один раз; папка в `.gitignore` |
| Пересборка backend: numpy, tokenizers, safetensors | около 20 МБ в образе | PyPI при `docker compose build` |
| Кэш векторов 49 документов (3006 чанков) | около 4 МБ | том Docker `app-dense` |

Модель не входит в образ: compose монтирует `./_local/models` в контейнер как `/models` (только чтение).

## Запуск на ноутбуке

1. Файлы модели лежат в `C:\Users\abUser\PycharmProjects\gpo2501\_local\models\rubert-mini-frida`
   (10 файлов, `model.safetensors` ~123 МБ). Если папки нет, скачайте файлы со страницы модели
   на Hugging Face в эту папку, сохранив подпапку `1_Pooling`.
2. Получите ветку с изменениями и пересоберите backend (сборка займёт несколько минут и ~1–2 ГБ RAM):

   ```bash
   docker compose up -d --build backend frontend
   ```

3. В `.env` должно быть `RAG_PROVIDER=search_only`, документы загружены в «Встроенную базу»
   (см. `docs/laptop-search-only.md`).
4. Откройте «Управление → Настройки → Движок ответов», включите **«Векторная добавка без Qdrant»**,
   каталог модели оставьте `/models/rubert-mini-frida`, сохраните.
5. Задайте в чате любой вопрос. Первый ответ придёт сразу (только BM25), а в фоне начнётся расчёт
   векторов всех чанков. Пока он идёт, ответы работают как раньше. Прогресс и готовность:
   `GET /api/v1/admin/rag/dense-status` (поле `cached_vectors` должно дойти до `chunks`).
   В облаке (4 ядра) расчёт 3006 чанков занял 250 с; на ноутбуке ориентируйтесь на 4–10 минут
   (оценка, проверьте). Расчёт грузит процессор, но по памяти лёгкий.
6. Дальше вектора берутся из кэша, новые документы досчитываются сами.

## Как снять замеры на ноутбуке

Память контейнера до включения добавки и после расчёта:

```bash
docker stats --no-stream
```

Качество и время на 17 вопросах (документы должны быть загружены; логин и пароль берутся из `.env`):

```bash
python scripts/eval_search.py --base-url http://localhost:5173 --label bm25  --out reports/eval_bm25.json
# включить добавку в настройках, дождаться cached_vectors = chunks
python scripts/eval_search.py --base-url http://localhost:5173 --label dense --out reports/eval_dense.json
```

Запишите из `docker stats` столбец MEM USAGE контейнера `backend` в обоих случаях.
Автотест хоста работает так же, как раньше: `python scripts/host_autotest.py --base-url http://localhost:5173`.

По вопросам (ранг нужного документа, было → стало):

* «Когда выплачивают стипендию?» не найден → 2-е место;
* «Какие документы нужны для поступления?» не найден → 2-е место;
* «Сколько стоит обучение на очной форме...?» не найден → 4-е место (синоним найден, но в тройку не попал);
* «Как оформить академический отпуск?» 2 → 1, «Какой размер повышенной стипендии...?» стал отвечаться без оператора;
* «Кто является учредителем ТУСУР?» стало хуже: 1 → 2 (остаётся в тройке);
* «Сколько стоит обучение на ФДО?» не найден ни там, ни там (возможно, нужного прайса нет в загруженных документах: проверьте).

Набор из 17 вопросов небольшой, поэтому разница в 1–2 вопроса — ориентир, а не доказательство.

## Как это устроено

* `backend/app/services/dense_local.py` — BERT-энкодер на numpy (проверен против `sentence-transformers`:
  косинус 1,0, максимальное отличие 1e-7), кэш векторов по sha1 текста чанка в `app-dense`, фоновый расчёт
  с файловой блокировкой между воркерами.
* Запрос получает префикс `search_query: `, чанки — `search_document: `, как требует модель.
* Списки BM25 и вектора склеивает RRF (`support_service._rrf_merge`). Оценка для маршрутизации — большая из двух:
  покрытие запроса BM25 и откалиброванный косинус (`DENSE_SCORE_FLOOR` 0,45 → 0, `DENSE_SCORE_CEIL` 0,75 → 1).
  Пороги подстраиваются в «Настройки → Маршрутизация».
* Чанки длиннее 256 токенов обрезаются (средний чанк ~205 токенов).
* Работает только при выключенном Qdrant (`VECTOR_SEARCH_ENABLED=false`); если файлов модели нет, поиск остаётся чистым BM25.
* Каждый воркер uvicorn держит свою копию модели (~120 МБ). В `compose.override.yml` backend запускается одним процессом;
  в продакшене с `--workers 4` памяти уйдёт заметно больше.
