# Техническая документация проекта (актуальный черновик)

Дата: 2026-04-02  
Статус: Draft v0.2 (web-only, актуализировано)

## 1. Цель документа

Зафиксировать текущее техническое состояние проекта, текущий уровень готовности и разрыв до стабильной web-версии MVP.

## 2. Актуальный продуктовый контур

### 2.1 Контур релиза

- В релизе: web-платформа техподдержки.
- Вне релиза: Telegram-бот (отложен).

### 2.2 Базовый пользовательский сценарий

1. Пользователь задает вопрос в `/support`.
2. Система выбирает режим `faq` или `rag`.
3. При недостаточных основаниях вопрос эскалируется в `operator`.
4. Админ управляет FAQ/источниками/reindex в `/admin-support`.

## 3. AS-IS (что есть сейчас)

### 3.1 Backend

- FastAPI + SQLModel + PostgreSQL.
- JWT-аутентификация, RBAC: роли `admin` / `operator` / `user` и разрешения
  (`app/core/permissions.py`). Колонки `is_superuser` в БД нет: это производное поле API.
- API поддержки, admin API базы знаний (источники, категории, тэги, документы, архив,
  reindex), API тикетов и отзывов.
- Логирование запросов/ответов: `request_journal` (все запросы) + `answer_journal`
  (шаги обработки `faq`/`rag`/`operator`/`human`), `active_request` — горячая очередь.

### 3.2 RAG/LLM

- Retrieval: Qdrant.
- Embeddings:
- `sentence-transformers` (локально, при доступности)
- Google embeddings fallback
- hash fallback
- Generation:
- Google AI Studio (`gemini-flash-latest`) primary
- Ollama fallback (`llama3.1:8b`)

### 3.3 Frontend

- React + Vite, TanStack Router/Query, shadcn-компоненты.
- Интерфейс строится по правам из `/users/me` (`permissions`, `role_name`):
  ссылки в сайдбаре, доступные вкладки и кнопки действий зависят от роли
  (см. `frontend/src/lib/permissions.ts`, `frontend/src/hooks/usePermissions.ts`).
- `/support`: вопрос, ответ с режимом и источниками, метрики решения, история обращений
  со шагами обработки и оценкой ответа (1–5 + комментарий).
- `/admin-support`: метрики, очередь и журнал запросов, тикеты (назначение/решение/
  переоткрытие), база знаний (метаданные, категория, тэги, история версий, reindex),
  документы, категории и тэги, поиск с фильтрами, частые вопросы. Состав вкладок и
  доступные действия зависят от прав.
- `/admin`: управление пользователями через выбор роли (справочник `GET /users/roles`).
- e2e (Playwright): логин, регистрация, сброс пароля, items, админка, профиль
  пользователя, smoke разделов поддержки и доступы ролей operator/user.

### 3.4 Инфраструктура

- Docker Compose: backend, frontend, db, qdrant, adminer, mailcatcher.
- Локальные проверки и тесты через docker/shell.

## 4. GAP-анализ

### 4.1 Функциональные разрывы

- Для стабильного FAQ требуется пополнение и чистка базы знаний (`source_type='faq'`).
- Для стабильного RAG требуется регулярная актуализация источников и документов + reindex.

### 4.2 Качественные разрывы

- Нужны регулярные smoke/regression проверки после обновления знаний.
- Нужна формализация troubleshooting и incident runbook.

### 4.3 Операционные разрывы

- Не зафиксирован минимальный release checklist в отдельном документе.
- Нет единой env-матрицы (обязательные/опциональные переменные).

## 5. Целевое состояние v0.1-draft

- Воспроизводимый web-only MVP.
- Предсказуемая маршрутизация `faq/rag/operator`.
- Управляемая админка знаний (FAQ + sources + reindex).
- Понятная процедура проверки и демонстрации.

## 6. План закрытия gap (практический)

### Этап A. Контент и знания

1. Наполнить базу знаний FAQ-записями (`source_type='faq'`, 10-30+).
2. Наполнить источники TUSUR (20+ страниц/документов) и разложить по категориям/тэгам.
3. Перепроверить reindex (источники + документы) и корректность source attribution.

### Этап B. Валидация логики

1. Проверить 3 сценария: `faq`, `rag`, `operator`.
2. Проверить цикл оператора: эскалация → назначение → решение → переоткрытие.
3. Прогнать backend-тесты (`scripts/tests-start.sh`, отдельная база `app_test`).
4. Прогнать UI e2e (`cd frontend && bunx playwright test`): логин, админка, профиль
   и smoke разделов поддержки.

### Этап C. Стабилизация

1. Добавить troubleshooting-гайд.
2. Зафиксировать release checklist.
3. Подготовить короткий runbook по деградациям (Google API, Qdrant, fallback).

## 7. Критерии готовности первой черновой версии

- Запуск и демонстрация без ручных правок кода.
- Понятная реакция системы в каждом из 3 режимов.
- Источники и confidence отображаются в ответах.
- Админ может обновить базу знаний и получить новый ответ после reindex.
- Оператор отвечает пользователю через API, запрос уходит из очереди, тикет можно переоткрыть.
- Отзыв сохраняется, метрика средней оценки видна в `/admin/metrics`.

## 8. Закрытые разрывы (внедрение целевой схемы)

Внедрена целевая схема БД (миграции M0–M10, план — `docs/db-schema-implementation-plan.md`):

- FAQ слился с базой знаний (`knowledge_source`, `source_type='faq'`), таблица `faqentry` удалена.
- Запросы: `request_journal` (все запросы) + `active_request` (горячая очередь), без переноса строк.
- Журнал ответов стал шагами (1:N): видно, на каком шаге и кем получен ответ.
- Появились таксономия (категории/тэги), независимый корпус документов с отдельной индексацией,
  архив версий знания и мягкое удаление источника.
- Тикеты: назначение агента, итоговое решение (уходит в журнал шагом `human`), переоткрытие.
- Отзывы: один на запрос, средняя оценка в метриках.
- RBAC вместо флага `is_superuser` (колонка удалена).

Остаются открытыми: гейт покрытия backend-тестами в CI (80% при пороге 90%),
единая env-матрица и release checklist, решение по таблице `item`,
nullable `app_user.role_id`, индивидуальные права пользователя (сейчас только роль).
